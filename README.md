# Умный Двор

Основа мультитенантной платформы для жителей домов и посёлков. Пользователь
входит в аккаунт, выбирает своё сообщество и открывает его обзор. Управляющий
видит участников своего сообщества; житель не имеет доступа к этому списку.
Обращения и другие бизнес-функции пока не реализованы.

## Стек

PHP 8.4, Laravel 13, PostgreSQL 17, Redis 7.4 / Predis, Inertia 3, Vue 3,
TypeScript, Tailwind CSS 4, Vite 8, PHPUnit 12. Интерфейс работает через
сессионные web-маршруты Inertia; отдельного REST API на этом этапе нет.

## Локальный запуск

На хосте нужны Git, Bash, Docker и Docker Compose v2. На Windows используйте
WSL2 с интеграцией Docker Desktop. PHP, Composer и Node.js работают внутри
контейнера. Команды выполняются из корня проекта от обычного пользователя,
имеющего доступ к Docker.

1. При первом запуске подготовьте `.env`, если его ещё нет:

   ```bash
   (umask 077; cp _dev/.env.example.development .env)
   ```

   Wrapper сам создаёт этот файл из того же шаблона, если он отсутствует.
   Корневая `.env.example` также согласована с Docker: PostgreSQL на
   `postgres:5432`, Redis на `redis:6379`, клиент `predis`. Для первого запуска
   рекомендуется шаблон `_dev/.env.example.development`.

2. Поднимите сервисы и установите зависимости из проекта:

   ```bash
   ./x up -b
   ```

   Флаг `-b` выполняет `composer install` и `npm install` внутри контейнера.
   Позже зависимости можно устанавливать отдельно через `./x composer install`
   и `./x npm ci`. Стек включает nginx, PHP-FPM, PostgreSQL и Redis.

3. Только если `APP_KEY` ещё пуст, сгенерируйте ключ приложения:

   ```bash
   ./x artisan key:generate --no-interaction
   ```

   После изменения настроек очистите кеш конфигурации, примените миграции
   и загрузите локальные демоданные:

   ```bash
   ./x artisan config:clear --no-interaction
   ./x artisan migrate --no-interaction
   ./x artisan db:seed --no-interaction
   ```

4. Запустите Vite и оставьте процесс работающим:

   ```bash
   ./x run dev
   ```

Откройте [приложение](http://localhost:3000). Это порт nginx из
`EXT_WEB_PORT`, а не порт Vite. При изменённых портах используйте свой адрес.
В development SSR обслуживает `@inertiajs/vite`; отдельный SSR-процесс не нужен.
Очередь и scheduler запускаются контейнером автоматически.

Остановка стека с сохранением данных:

```bash
./x down
```

Подробности wrapper находятся в [_dev/README.md](_dev/README.md).

доступен обзор, а в «Лесном» — также список участников. Прямой запрос списка
участников «Соснового» возвращает 403. Для `resident1@example.test` чужой
«Лесной» возвращает 404.

## Тесты и проверки

Тесты используют отдельную PostgreSQL-БД **`saas_test_testing`** и
`RefreshDatabase`. Один раз создайте эту БД в локальном PostgreSQL, если её
ещё нет:

```bash
./x artisan tinker --execute 'DB::statement("CREATE DATABASE saas_test_testing");' --no-interaction
```

Затем подготовьте тестовое окружение, если `.env.testing` ещё не существует:

```bash
(umask 077; cp .env.testing.example .env.testing)
./x artisan key:generate --env=testing --no-interaction
./x artisan config:clear --no-interaction
```

При изменении локальных реквизитов PostgreSQL обновите также `.env.testing`.
Не указывайте в нём рабочую БД. `phpunit.xml` принудительно задаёт testing,
PostgreSQL и имя тестовой БД, а `Tests\TestCase` проверяет подключение до
выполнения тестовых миграций. Таблицы тестовой БД могут пересоздаваться.

```bash
./x artisan test --compact
./x artisan test --compact tests/Feature/Database/DemoSeederTest.php
./x composer exec -- pint --dirty --format agent
./x npm run typecheck
./x npm run build
```

`build` собирает и клиент, и SSR. Чтобы проверить собранное приложение без
Vite dev server, остановите `./x run dev`, выполните сборку и в отдельном
терминале запустите:

```bash
./x artisan inertia:start-ssr --no-interaction
```

Эта команда обслуживает SSR собранных ресурсов; сама сборка не запускает
SSR-сервис. Автоматические Feature-тесты проверяют HTTP/Inertia-контракт,
но не заменяют проверку интерфейса и гидратации в браузере.

## Модульная архитектура и изоляция

- `app/Modules/Identity`: User, вход/выход, LoginRequest и действия сессии.
- `app/Modules/Communities`: Community, CommunityMember, enum CommunityRole,
  CurrentCommunity, middleware, policy, контроллеры и действия выборки данных.
- `routes/web.php`: общие сессионные маршруты приложения.
- `app/Http/Middleware/HandleInertiaRequests.php`: безопасные shared props.
- `resources/js/pages` и `resources/js/layouts`: Vue-страницы и общий layout.
- `database/migrations`, `database/factories`, `database/seeders`: схема и данные.

Контроллеры отвечают за HTTP/Inertia, действия — за выборки. Роль хранится
в членстве, поэтому один пользователь может быть жителем в одном сообществе
и управляющим в другом.

| Маршрут | Доступ |
| --- | --- |
| `GET /` | Гостю — login, вошедшему — список сообществ, даже если оно одно |
| `GET/POST /login` | Гости; POST ограничен по email/IP |
| `POST /logout` | Авторизованный пользователь |
| `GET /communities` | Только свои сообщества; без членств — пустой список |
| `GET /communities/{community:slug}/dashboard` | Любой участник текущего сообщества |
| `GET /communities/{community:slug}/members` | Только manager текущего сообщества |

`auth` проверяется до привязки модели по slug. `ResolveCommunity` на каждом
запросе заново проверяет членство и заполняет scoped `CurrentCommunity`.
Чужой или несуществующий tenant возвращает 404; resident на своём списке
участников — 403. Policy повторно проверяет доступ к переданному сообществу.
Контекст очищается в `finally`, в том числе при исключениях.

Клиент не выбирает права через `community_id`, `user_id` или `role`. Запросы
списков ограничены пользователем либо проверенным текущим сообществом.
В `auth.user` передаются только id/name/email, а в `community` —
id/name/slug/role. На login и списке сообществ `community` равен null.
Контекст, текущий пользователь и ссылки обновляются также при частичных
запросах Inertia. Скрытая ссылка не заменяет серверную авторизацию.

### Модуль Requests

Модуль обращений реализован и работает в рамках текущего сообщества.
Все действия проходят через `auth` + `community` middleware, при этом
`CurrentCommunity` используется как источник tenant-контекста, а все запросы
к `service_requests` ограничены текущим сообществом и ролями пользователя.

Основные маршруты:

| Маршрут | Доступ |
| --- | --- |
| `GET /communities/{community:slug}/requests` | любой участник, с фильтрацией по своему tenant |
| `GET /communities/{community:slug}/requests/create` | только resident |
| `POST /communities/{community:slug}/requests` | только resident |
| `GET /communities/{community:slug}/requests/{request}` | участник сообщества, видит свой или все обращения для manager |
| `POST /communities/{community:slug}/requests/{request}/messages` | resident или manager, если может просматривать обращение |
| `PATCH /communities/{community:slug}/requests/{request}/status` | только manager текущего сообщества |

Логика модуля:

- статус обращения хранится в enum `RequestStatus` и допускает только переходы `new -> in_progress`, `new -> resolved`, `in_progress -> resolved`, `resolved -> in_progress`;
- при создании записи сервер автоматически создаёт первую историю `null -> new` и не принимает `community_id`, `user_id`, `status` и `resolved_at` из запроса;
- комментарии обновляют `updated_at` родительского обращения, но не меняют статус;
- `resolved_at` выставляется при переходе в `resolved` и сбрасывается при повторном открытии;
- все изменения статуса и истории проходят в одной транзакции с повторной проверкой допустимого перехода после блокировки строки.

Демонстрационные данные создаются через `RequestDemoSeeder`: в двух сообществах есть шесть обращений, история и комментарии согласованы с ролями жителей и управляющих. Повторный запуск seed не дублирует записи и не сбрасывает существующий статус.

Проверки выполняются через:

```bash
./x artisan test --compact tests/Feature/Requests
./x artisan test --compact tests/Feature/Database
./x composer exec -- pint --dirty --format agent
./x npm run typecheck
./x npm run build
```

# Платформа для жителей домов и посёлков

За 24 часа создайте с нуля MVP мультитенантной SaaS-платформы.
Помогите жителям и управляющим решить одну повседневную
задачу.

## Зачем нужен сервис

В домовом чате легко пропустить объявление о ремонте или потерять ответ на заявку.
Платформа должна дать каждому коттеджному посёлку или многоквартирному дому
своё пространство, где жители могут обратиться к управляющему и узнать, как решается
их вопрос.

## Для кого вы проектируете

### Житель

Хочет быстро решить бытовой вопрос и понять, нужен ли от него следующий шаг.

### Представитель сообщества

Председатель ТСЖ, руководитель посёлка или сотрудник управляющей компании
подключает сообщество к платформе и организует работу с жителями.

## Что взять в MVP

Выберите задачу, которую стоит решить первой. Вот несколько примеров.

- Обращения о проблемах в доме
- Заказ услуг, например уборки
- Новости и объявления
- Гостевые и транспортные пропуска
- Голосования жителей
- Управление шлагбаумом

Вы можете предложить и свою задачу. Состав MVP, интерфейс, архитектуру и стек
определяете вы. Готовые библиотеки и ИИ-инструменты допустимы.

# Демонстрация и оценка

## Сквозной сценарий

Подготовьте веб-приложение, в котором можно пройти выбранный сценарий от начала
до конца. Например, житель сообщает о неисправности, управляющий отвечает,
а житель при следующем входе видит ответ. Пользователю должно быть понятно, к чему
привело его действие. Если нужен внешний сервис или устройство, его работу можно
имитировать.

## Доступ и границы сообществ

Подготовьте два демонстрационных сообщества в одном приложении. Пользователь
входит под своей учётной записью и может выполнять только действия, доступные его
роли. Данные чужого сообщества должны быть закрыты для чтения и изменения, в том
числе по прямой ссылке или запросу к серверу.
