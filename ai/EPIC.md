# Задача №1. Основа мультитенантной SaaS-платформы для жителей

## 1. Контекст проекта

Разрабатываем MVP веб-платформы для жителей многоквартирных домов и коттеджных посёлков.

Основной функциональный сценарий: житель создаёт обращение о бытовой проблеме, управляющий отвечает и изменяет статус, житель видит результат.

Приложение мультитенантное: несколько независимых сообществ работают в одной системе, но их данные изолированы.

На первом этапе необходимо создать архитектурную основу приложения, реализовать сообщества, авторизацию, роли, определение текущего сообщества и безопасность доступа.

**Не реализовывать на этом этапе бизнес-функциональность обращений.** Она будет отдельной задачей.

## 2. Принципы архитектуры

Применить облегчённую модульную архитектуру — Modular Monolith.

Основные модули:

### Identity

Отвечает за:

- пользователей;
- авторизацию;
- аутентификацию;
- профиль текущего пользователя.

### Communities

Отвечает за:

- сообщества;
- участников;
- роли участников;
- определение текущего сообщества;
- проверку доступа к сообществу.

### Requests

Будущий модуль обращений.

На этом этапе создать только каталог модуля, если это соответствует выбранной структуре проекта. Не создавать фиктивные классы без функциональности.

Предпочтительная структура:

```text
app/
  Modules/
    Identity/
      Models/
    Communities/
      Models/
      Enums/
      Http/
        Controllers/
        Middleware/
      Policies/
      Actions/
    Requests/
  Http/
  Providers/

resources/js/
  components/
  layouts/
  pages/
    Auth/
    Communities/
  types/
```

Структура ориентировочная. При необходимости адаптировать её к выбранной архитектуре, сохраняя понятные границы модулей.

Не создавать сложную систему автоматической регистрации модулей. Допускается явная регистрация маршрутов, middleware и policies через стандартные механизмы Laravel.

## 3. Модель данных

### users

Использовать стандартную таблицу пользователей Laravel.

Поля:

- id
- name
- email (unique)
- password
- timestamps

### communities

Поля:

- id
- name
- slug (unique)
- description (nullable)
- timestamps

Модель: Community.

### community_members

Поля:

- id
- community_id
- user_id
- role
- timestamps

Ограничения:

- foreign key community_id → communities.id
- foreign key user_id → users.id
- unique(community_id, user_id)
- индекс по user_id

Модель: CommunityMember.

Роли через PHP Enum:

```php
enum CommunityRole: string
{
    case Resident = 'resident';
    case Manager = 'manager';
}
```

Использовать Eloquent casts для enum.

### Связи

User:

- belongsToMany Community через community_members
- hasMany CommunityMember

Community:

- belongsToMany User
- hasMany CommunityMember

CommunityMember:

- belongsTo User
- belongsTo Community

Не использовать глобальное поле role в users.

Один пользователь может состоять в нескольких сообществах и иметь разные роли.

## 4. Авторизация

Реализовать стандартную session-based авторизацию Laravel.

Требования:

- Вход по email и паролю.
- Выход из системы.
- Защита маршрутов через auth middleware.
- CSRF-защита.
- Безопасное хранение паролей через стандартный Laravel hashing.
- Регенерация сессии после входа.
- Инвалидация сессии и регенерация CSRF-токена после выхода.

Публичная регистрация пользователей пока не требуется.

Пользователи создаются через seeders.

Не реализовывать API-токены и JWT.

## 5. Определение текущего сообщества

Использовать маршруты вида:

```text
/communities/{community:slug}/dashboard
/communities/{community:slug}/members
```

Создать middleware ResolveCommunity.

Алгоритм:

1. Получить сообщество из route model binding.
2. Проверить, что пользователь аутентифицирован.
3. Проверить, что пользователь состоит в сообществе.
4. Если членство отсутствует — вернуть HTTP 404.
5. Сохранить текущий Community и CommunityMember в request-scoped контексте.
6. Передать выполнение дальше.

Контекст сообщества должен быть доступен контроллерам и сервисам через отдельный класс CurrentCommunity.

Требования к CurrentCommunity:

- Содержит текущий Community.
- Содержит CommunityMember текущего пользователя.
- Предоставляет методы получения сообщества и роли.
- Регистрируется в Laravel Container через scoped binding.
- Не использует static-переменные или глобальное изменяемое состояние.
- При отсутствии установленного контекста выдаёт понятное исключение.

Не определять текущее сообщество из произвольного параметра тела запроса.

Не использовать community_id из клиентских данных как доверенный источник.

## 6. Разграничение прав

Реализовать CommunityPolicy или эквивалентные Laravel Gates.

Правила:

Resident:

- Может просматривать dashboard своего сообщества.
- Не может просматривать список участников через административный маршрут.
- Не может управлять сообществом.

Manager:

- Может просматривать dashboard.
- Может просматривать список участников своего сообщества.
- В будущем сможет управлять обращениями.

Оба типа пользователей:

- Не могут просматривать чужое сообщество.
- Не могут обращаться к данным чужого сообщества по прямой ссылке.
- Не могут изменять свою роль через HTTP-запрос.
- Не могут назначать себя управляющим.

Для отсутствующего членства возвращать 404.

Для недостаточных прав внутри доступного сообщества возвращать 403.

Все проверки выполнять на сервере.

## 7. HTTP-маршруты

Реализовать:

```text
GET  /login
POST /login
POST /logout

GET  /
GET  /communities

GET  /communities/{community:slug}/dashboard
GET  /communities/{community:slug}/members
```

Поведение:

GET /:

- Неавторизованный пользователь → login.
- Авторизованный → список доступных сообществ или перенаправление на единственное сообщество.

GET /communities:

- Показывает только сообщества текущего пользователя.

GET dashboard:

- Доступен resident и manager своего сообщества.

GET members:

- Доступен только manager своего сообщества.

Маршруты сообщества должны проходить через ResolveCommunity.

## 8. Frontend

Использовать Inertia + Vue 3 + TypeScript.

Создать:

### Login

Форма:

- email
- password
- кнопка входа
- вывод ошибок валидации

### Communities/Index

Список сообществ пользователя.

Для каждого:

- название;
- описание;
- роль пользователя;
- кнопка перехода в сообщество.

### Communities/Dashboard

Отображает:

- название сообщества;
- текущего пользователя;
- его роль;
- приветственный текст;
- навигацию;
- заглушку будущего раздела обращений.

### Communities/Members

Простая таблица участников:

- имя;
- email;
- роль.

Доступ только manager.

### Layout

Создать единый авторизованный layout:

- название приложения;
- название текущего сообщества;
- навигация;
- имя пользователя;
- кнопка выхода.

Интерфейс должен быть аккуратным, адаптивным и ориентированным на обычного жителя, а не на разработчика.

Использовать Tailwind CSS.

Не добавлять тяжёлые UI-библиотеки без необходимости.

## 9. Inertia shared props

Передавать в Inertia:

```ts
auth: {
  user: {
    id: number;
    name: string;
    email: string;
  } | null;
}

community: {
  id: number;
  name: string;
  slug: string;
  role: 'resident' | 'manager';
} | null;
```

Не передавать:

- пароль;
- password hash;
- remember token;
- внутренние служебные данные моделей;
- список всех сообществ системы.

Текущий community передавать только после успешной проверки членства.

## 11. Автоматические тесты

Написать Feature-тесты.

Обязательные сценарии:

1. Гость не может открыть dashboard.
2. Гость перенаправляется на login.
3. Пользователь может войти с корректными данными.
4. Неверный пароль отклоняется.
5. Пользователь может выйти.
6. Пользователь видит только свои сообщества.
7. Resident сообщества №1 может открыть свой dashboard.
8. Resident сообщества №1 не может открыть dashboard сообщества №2.
9. Manager сообщества №1 не может открыть dashboard сообщества №2.
10. Resident не может открыть список участников.
11. Manager может открыть список участников своего сообщества.
12. Manager не может открыть список участников чужого сообщества.
13. Пользователь с двумя членствами получает правильную роль в каждом сообществе.
14. Подмена slug в URL не даёт доступа к чужим данным.
15. Удалённое членство немедленно лишает пользователя доступа при следующем запросе.

Использовать RefreshDatabase.

Проверять HTTP-статусы и фактическую изоляцию данных, а не только наличие middleware.
