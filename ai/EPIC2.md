# Задача №2. Реализация модуля Requests — обращения жителей

## 1. Контекст проекта

Разрабатывается MVP мультитенантной SaaS-платформы для жителей многоквартирных домов и коттеджных посёлков.

Технологический стек:

- PHP 8.4+
- Laravel 13
- PostgreSQL
- Inertia.js
- Vue 3 (Composition API)
- TypeScript
- Tailwind CSS
- Vite

Архитектура — облегчённый модульный монолит.

На предыдущем этапе реализованы:

- Модуль Identity.
- Модуль Communities.
- Пользователи и session-based авторизация.
- Сообщества и участники.
- Роли `resident` и `manager`.
- Middleware `ResolveCommunity`.
- Request-scoped сервис `CurrentCommunity`.
- Проверка членства в сообществе.
- Два демонстрационных сообщества.

Перед началом работы изучи фактическую структуру репозитория. Не предполагай, что все перечисленные классы уже существуют или имеют указанные имена.

Используй существующие соглашения проекта.

**Цель текущей задачи:** реализовать модуль обращений жителей с полноценным сквозным сценарием, интерфейсом, разграничением прав и автоматическими тестами.

Не реализовывать функциональность, не относящуюся к обращениям.

## 2. Пользовательские сценарии

### Сценарий 1. Житель создаёт обращение

1. Житель входит в приложение.
2. Выбирает своё сообщество.
3. Переходит в раздел «Обращения».
4. Нажимает «Создать обращение».
5. Заполняет заголовок и описание.
6. Отправляет форму.
7. Система создаёт обращение со статусом `new`.
8. Житель попадает на страницу созданного обращения.
9. Видит номер, статус, описание и дату создания.

Обращение автоматически привязывается к текущему сообществу и авторизованному пользователю.

### Сценарий 2. Управляющий обрабатывает обращение

1. Управляющий входит в своё сообщество.
2. Открывает раздел обращений.
3. Видит обращения всех жителей своего сообщества.
4. Открывает новое обращение.
5. Переводит его в статус `in_progress`.
6. Добавляет комментарий.
7. При необходимости переводит обращение в статус `resolved`.

Все изменения сохраняются в базе данных.

### Сценарий 3. Житель получает ответ

1. Житель повторно входит в приложение.
2. Открывает список обращений.
3. Видит актуальный статус.
4. Открывает обращение.
5. Видит комментарий управляющего и историю изменений.
6. Может написать дополнительный комментарий.

### Сценарий 4. Изоляция сообществ

1. Пользователь сообщества A создаёт обращение.
2. Пользователь сообщества B пытается открыть его через URL.
3. Сервер возвращает HTTP 404.
4. Пользователь B не может прочитать, изменить статус или добавить комментарий.
5. Управляющий сообщества B также не получает доступ к обращению сообщества A.

Изоляция должна обеспечиваться сервером, а не только интерфейсом.

## 4. Модель данных

### 4.1. Таблица service_requests

Поля:

| Поле | Тип | Назначение |
|---|---|---|
| id | bigint, PK | Идентификатор |
| community_id | foreignId | Сообщество |
| user_id | foreignId | Автор обращения |
| title | varchar(255) | Заголовок |
| description | text | Описание |
| status | varchar(32) | Текущий статус |
| created_at | timestamp | Дата создания |
| updated_at | timestamp | Дата изменения |
| resolved_at | timestamp nullable | Дата решения |

Ограничения:

- `community_id` — обязательный внешний ключ.
- `user_id` — обязательный внешний ключ.
- Индекс `(community_id, status)`.
- Индекс `(community_id, created_at)`.
- Индекс `(community_id, user_id, created_at)`.
- Статус по умолчанию `new`.

Использовать модель `ServiceRequest`.

Связи:

- belongsTo Community.
- belongsTo User (автор).
- hasMany RequestMessage.
- hasMany RequestStatusHistory.

Дополнительно обеспечить на уровне бизнес-логики, что автор обращения является участником указанного сообщества.

Не принимать `community_id`, `user_id` и `status` из формы создания обращения.

### 4.2. Таблица request_messages

Поля:

| Поле | Тип | Назначение |
|---|---|---|
| id | bigint, PK | Идентификатор |
| service_request_id | foreignId | Обращение |
| user_id | foreignId | Автор сообщения |
| body | text | Текст |
| created_at | timestamp | Дата создания |
| updated_at | timestamp | Дата изменения |

Связи:

- belongsTo ServiceRequest.
- belongsTo User.

Сообщения не редактируются и не удаляются в MVP.

Идентификатор сообщества определяется через родительское обращение.

Не разрешать добавление сообщений к обращениям из чужого сообщества.

### 4.3. Таблица request_status_histories

Поля:

| Поле | Тип | Назначение |
|---|---|---|
| id | bigint, PK | Идентификатор |
| service_request_id | foreignId | Обращение |
| user_id | foreignId nullable | Кто изменил статус |
| from_status | varchar(32), nullable | Предыдущий статус |
| to_status | varchar(32) | Новый статус |
| created_at | timestamp | Время изменения |

Использовать отдельную модель `RequestStatusHistory`.

История должна фиксировать:

- Создание обращения со статусом `new`.
- Переход в `in_progress`.
- Переход в `resolved`.
- Повторное открытие обращения, если оно предусмотрено правилами ниже.

Историю не разрешается редактировать через HTTP.

## 5. Статусы и переходы

Создать enum:

```php
enum RequestStatus: string
{
    case New = 'new';
    case InProgress = 'in_progress';
    case Resolved = 'resolved';
}
```

Допустимые переходы:

| Текущий статус | Следующий статус | Кто может |
|---|---|---|
| new | in_progress | manager |
| new | resolved | manager |
| in_progress | resolved | manager |
| resolved | in_progress | manager |

Переход `resolved → in_progress` используется для повторного открытия обращения управляющим.

Запрещены:

- Изменение статуса жителем.
- Переход в тот же статус.
- Неизвестные статусы.
- Изменение статуса пользователем другого сообщества.

При переходе в `resolved` устанавливать `resolved_at`.

При повторном открытии сбрасывать `resolved_at` в null.

Каждый переход должен создавать запись в истории.

Изменение статуса и запись истории должны выполняться атомарно, в одной транзакции.

Для защиты от конкурентных изменений использовать блокировку строки обращения `lockForUpdate()` внутри транзакции.

Проверять допустимость перехода после получения блокировки.

## 6. Правила доступа

### Resident

Может:

- Создавать обращения в своём сообществе.
- Просматривать список только своих обращений.
- Просматривать собственное обращение.
- Добавлять комментарии к собственному обращению.

Не может:

- Просматривать обращения других жителей.
- Изменять статус.
- Удалять обращения.
- Редактировать чужие сообщения.

### Manager

Может:

- Просматривать все обращения своего сообщества.
- Просматривать конкретное обращение.
- Добавлять комментарии.
- Изменять статус.

Не может:

- Просматривать обращения другого сообщества.
- Изменять чужое сообщество.
- Подменять автора комментария.
- Удалять историю статусов.

Для MVP управляющий не создаёт обращения от имени жителей.

### Важное требование

Проверка доступа должна учитывать одновременно:

1. Аутентифицированного пользователя.
2. Его членство в текущем сообществе.
3. Роль в текущем сообществе.
4. Принадлежность обращения текущему сообществу.
5. Авторство обращения для resident.

Реализовать `ServiceRequestPolicy`.

Использовать `authorize()` или стандартный механизм Laravel Authorization.

Не дублировать сложные проверки прав в контроллерах.

При недостаточных правах внутри своего сообщества возвращать 403.

При попытке доступа к обращению другого сообщества возвращать 404.

Для предотвращения IDOR получать обращение только через запрос, ограниченный текущим сообществом:

```php
$serviceRequest = ServiceRequest::query()
    ->where('community_id', $currentCommunity->id())
    ->findOrFail($id);
```

Не использовать обычный `ServiceRequest::findOrFail($id)` для обработки tenant-scoped маршрутов.

Не полагаться только на Policy для изоляции сообществ.

## 7. HTTP-маршруты

Все маршруты должны быть защищены:

- `auth`
- `ResolveCommunity`

Использовать существующую систему маршрутов проекта.

Предпочтительная структура:

```text
GET    /communities/{community:slug}/requests
GET    /communities/{community:slug}/requests/create
POST   /communities/{community:slug}/requests
GET    /communities/{community:slug}/requests/{request}
POST   /communities/{community:slug}/requests/{request}/messages
PATCH  /communities/{community:slug}/requests/{request}/status
```

Использовать именованные маршруты.

Для `{request}` допустимо использовать идентификатор обращения.

Не допускать, чтобы implicit route model binding загружал обращение из другого сообщества до tenant-scoped проверки.

Если используется кастомный binding, он должен явно ограничивать выборку текущим сообществом.

Для упрощения можно принимать scalar ID и загружать обращение через отдельный метод, выполняющий tenant-scoped query.

## 8. Backend: бизнес-операции

### 8.1. CreateRequest

Входные данные:

- title
- description

Контекст:

- CurrentCommunity
- Authenticated User

Алгоритм:

1. Проверить роль пользователя.
2. Валидировать входные данные.
3. Создать ServiceRequest.
4. Установить community_id из CurrentCommunity.
5. Установить user_id из текущего пользователя.
6. Установить статус `new`.
7. Создать запись истории со статусом `new`.
8. Вернуть созданное обращение.

Создание обращения и истории выполнять в одной транзакции.

### 8.2. AddRequestMessage

Входные данные:

- serviceRequest
- body

Алгоритм:

1. Проверить доступ к обращению.
2. Проверить, что обращение принадлежит текущему сообществу.
3. Создать сообщение.
4. Установить user_id из Auth.
5. Вернуть сообщение.

Комментарии разрешены для всех статусов, включая `resolved`.

Добавление комментария не меняет статус автоматически.

### 8.3. ChangeRequestStatus

Входные данные:

- serviceRequest
- targetStatus

Алгоритм:

1. Проверить права manager.
2. Открыть транзакцию.
3. Заблокировать запись обращения.
4. Проверить текущий статус.
5. Проверить допустимость перехода.
6. Обновить статус.
7. Обновить resolved_at.
8. Добавить запись истории.
9. Завершить транзакцию.

В случае недопустимого перехода вернуть ошибку валидации, понятную пользователю.

## 11. Представление данных в Inertia

Не передавать Eloquent-модели целиком без контроля сериализации.

Использовать явное формирование данных через Resources, DTO или аналогичный существующий механизм проекта.

Для списка обращений передавать только необходимые поля.

Пример структуры:

```ts
interface ServiceRequest {
    id: number;
    title: string;
    description: string;
    status: 'new' | 'in_progress' | 'resolved';
    created_at: string;
    updated_at: string;
    resolved_at: string | null;
    author: {
        id: number;
        name: string;
    };
}
```

Для страницы просмотра дополнительно передавать комментарии и историю статусов.

Не передавать:

- Данные других сообществ.
- Пароли.
- Внутренние служебные поля.
- Неиспользуемые отношения моделей.

Формат дат должен быть единообразным.

## 13. Автоматические тесты

Написать Feature-тесты.

7. Нельзя подменить user_id.
8. Нельзя установить status через форму.
9. Создание обращения создаёт запись истории.
10. Обращение и история создаются атомарно.

12. Resident не видит обращения другого жителя того же сообщества.

15. Прямой URL чужого обращения возвращает 404.
16. Список обращений не содержит чужих данных.
17. Фильтрация по статусу работает корректно.

### Комментарии

19. Resident может комментировать своё обращение.
20. Resident не может комментировать чужое обращение.
21. Manager может комментировать обращение своего сообщества.
22. Manager не может комментировать обращение чужого сообщества.
23. Нельзя подменить user_id комментария.
24. Комментарий не изменяет статус.
25. Можно комментировать resolved-обращение.

### Статусы

26. Manager может перевести new → in_progress.
27. Manager может перевести in_progress → resolved.
28. Manager может перевести new → resolved.
29. Manager может повторно открыть resolved → in_progress.
30. Resident не может изменить статус.
31. Manager другого сообщества не может изменить статус.
32. Недопустимый переход отклоняется.
33. Повторная установка текущего статуса отклоняется.
34. Изменение статуса создаёт запись истории.
35. resolved_at устанавливается корректно.
36. resolved_at сбрасывается при повторном открытии.

### Мультитенантность

37. Пользователь сообщества A не может прочитать обращение сообщества B.
38. Пользователь сообщества A не может комментировать обращение сообщества B.
39. Пользователь сообщества A не может изменить статус обращения сообщества B.
40. Пользователь с членством в двух сообществах получает доступ к обращениям согласно роли в каждом из них.
41. Удаление членства лишает доступа к обращениям.
42. Подмена URL, параметров формы или идентификаторов не обходит tenant isolation.

Использовать RefreshDatabase.

Проверять не только HTTP-статусы, но и фактическое состояние базы данных.

## 14. Производительность

Для MVP достаточно стандартных возможностей Laravel.

Требования:

- Использовать индексы.
- Использовать eager loading.
- Исключить N+1 в списках.
- Использовать пагинацию.
- Не загружать обращения всех сообществ с последующей фильтрацией в PHP.
- Не использовать Redis и очереди без необходимости.

Для истории отдельного обращения допускается загрузка всех событий, поскольку в MVP объём ограничен.

Не реализовывать преждевременную оптимизацию.
